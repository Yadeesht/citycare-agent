    - Tool round trip, with each result paired to its tool_use.
    - Parallel tools run concurrently and return in one user message.
    - Unknown tool, invalid input, tool exception and timeout all come back as
      tool errors.
    - A denying or crashing hook means the tool is never called.
    - A rewrite is re-validated.
    - Identity is read-only and comes from the context, not the model's
      arguments.
    - Max iterations, budget, max_tokens, refusal, pause_turn and LLM exceptions
      each stop the loop without raising.
    - Usage, cost and trace events add up.
  - Orchestrator:
    - The transcript is shared across workers and sessions are isolated.
    - A gate short-circuits before the router and worker, runs on every turn,
      and a crashing gate is skipped.

    - State persists across turns while flags reset.

    - LLMRouter handles bad output, including a model call that fails.

  How context works today

  There is no per-agent memory. Three kinds of context exist, and each agent run
  builds its window fresh from them.

  1. The shared transcript (Session.history) holds plain text only.
  - It stores each user message and each agent's final reply, and nothing else.
  - Tool calls, tool results and thinking blocks are discarded when a turn ends.
  - It is capped at 40 messages, trimmed from the front to start on a user
    message. There is no summarising.

  2. State (ctx.state) lives in code and persists for the session. It holds:
  - the pending read-back
  - the failure counter
  - the booking epoch
  - language
  - handed_off
  - now

  The model never sees state, except that now becomes the date and calendar
  block in the booking and billing system prompts.

  3. Flags (ctx.flags) are per turn, for handoff and emergency. The model never
  sees them either.

  What each component sees

  Component: Router
  Sees: Its own system prompt, the last 6 transcript messages, the new message,
    and the route tool.
  Doesn't see: Tool results, state, hospital data, which agent said what, or the

    date.
  ────────────────────────────────────────
  Component: Booking / billing
  Sees: Its own system prompt (with the date), the transcript of up to 40
    messages and the new message, plus this turn's tool calls, results and
    thinking while the run is live.
  Doesn't see: The other agents' tools or tool results, or any earlier turn's
    tool results.
  ────────────────────────────────────────
  Component: Info
  Sees: A static prompt with hospital_info.md, plus the transcript.
  Doesn't see: Everything about the hospital system, since it has no tools.
  ────────────────────────────────────────
  Component: Gates, human, safety
  Sees: Only the raw message, state and language detection.
  Doesn't see: No model is involved.

  So each agent has its own window, built fresh every turn. They are linked only
  by the text transcript, and nothing persists inside an agent between turns.

  Consequences

  - Tool results don't carry over. If booking lists your appointments in turn 1,
    it has to call the tool again in turn 2, because only its reply text
    survives. That costs a call, but the data is always fresh.
  - "Yes" depends on the transcript. The model has to rebuild the tool arguments
    from its own read-back text. If it gets them slightly wrong, the hook sees
    a different action and demands a new read-back. That is safe but can be
    annoying, and it isn't covered by a test with a real model.
  - Billing doesn't see booking's data. It only sees booking's text replies.
    That is fine for the "bill, then book" flow.
  - Cost grows with chat length. Every call resends the whole transcript. Only
    the system prompt and tools are cached, not the messages.
  - The router's 6-message window is small. It's enough for a "yes" after a
    read-back but not for a long topic shift.
  - Pending actions are tied to no agent. Whichever agent the router picks can
    finish the action, as long as the arguments match. This is arguably safer
    than sticky routing, but a wrong route after a read-back means the patient
    has to confirm again.

  If you'd rather change this, the options are to store a short structured
  summary of tool results in the transcript, to widen the router window, or to
  give the router the pending read-back explicitly. Which direction do you want?
